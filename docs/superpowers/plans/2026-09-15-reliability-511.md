# Issue #511 Reliability Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop thinking from eating the output limit, stop invalid confirmation answers from discarding good checks, separate replay crashes from missing recordings, and stop counting jobs that completed in their own transaction as failures.

**Architecture (as shipped):** The narrative client sends no thinking field, so frame verification and confirmation keep the model's default thinking with room to finish: frame verification gets at least 16,000 output tokens, and confirmation 16,000 tokens with a 300 s timeout. Confirmation keeps its free-text JSON answer, validated in code with rule codes. It gets one retry; a refusal is not retried, and an answer still invalid is staged `unavailable` through the unavailable-retry table (retried after 1, 6 and 24 hours; the fourth unavailable attempt is permanent). Frame capture sends replay events in 1 MiB batches, enforces its wall-clock budget over the whole browser phase, classifies crashes, and always closes its browser and loopback server. The job trace, the job counters and the poller share one predicate for "this throw means the job finished".

> **Superseded parts of this plan.** Tasks 2-4 and 6-7 were written for a strict `submit_confirmation` tool with a corrective retry (`NarrativeClient.callTool`) and for sending thinking disabled. The Task 9 accuracy checks rejected both, so that code was removed before merge. The retry schedule also changed from "third attempt permanent" to 1, 6 and 24 hours. Read "Outcome of the accuracy checks (Task 9)" below for what shipped. The superseded steps are kept as the record of what was planned.

**Tech Stack:** Node 22, strict ESM TypeScript, `@anthropic-ai/sdk` 0.120.0, Vitest, `playwright-core` 1.62.1, PostgreSQL job queue.

**Spec:** GitHub issue [#511](https://github.com/opslane/opslane/issues/511) (read it in full: `gh issue view 511 --repo opslane/opslane`). Related rule source: #517. Epic decisions: #515.

## Decisions this plan makes (the issue left them open)

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | Does the corrective retry's second model call count against `FRICTION_CONFIRM_DAILY_CAP`? | No. One reserved unit covers one recording read, including its single corrective retry. | The cap is a circuit breaker on recording reads, not a token meter; the meter already records both calls in `job_usage`. Charging twice would let invalid answers exhaust a day. |
| D2 | Which calls send thinking disabled? | Frame verification and confirmation send `disabled`. Narration, cheap matching and first look keep `model_default` (field omitted), which is their behavior today. **Superseded** by the outcome of the accuracy checks below: every call uses the model's default thinking, and the client has no thinking option. | The issue measured cut-offs only on verification and confirmation. Changing narration or first-look behavior needs its own accuracy check. `model_default` also stays valid on Haiku 4.5, which rejects `adaptive`. |
| D3 | How are crashes counted apart from missing recordings? | The `unavailable` attempt's `note` names the reason (`UNAVAILABLE_NOTES`), and the warning log carries `unavailable_reason`. | No migration. Unavailable notes are never read by customer surfaces: `previewCohort` keeps confirmed notes only and every Go reader joins `friction_checks`, which excludes unavailable attempts. |
| D4 | Does `JobRescheduledError` get the same treatment as `JobCompletedInTransaction`? | Yes. | The poller already treats both as `completed` (`poller.ts:209-213`). Leaving rescheduled jobs as trace errors and failed-job counts is the same defect at the same seam. |
| D5 | What happens when the one-fix gate answers invalidly twice inside a confirmation job? | The batch still finalizes; the plan is left unjudged so `applyConfirmationTransition` sets `reconcile_needed` instead of publishing. | Today it throws, which dead-letters the batch and discards valid checks. Publishing past an unanswered gate could ship a duplicate. Reconciliation retries on its 15-minute tick. |
| D6 | Blind retry or corrective retry? | Corrective: the retry replays the rejected assistant turn verbatim (thinking blocks included, which a thinking-on retry requires) and returns an `is_error` tool result that names the broken rule. **Superseded** by the outcome of the accuracy checks below: confirmation answers in free-text JSON with one blind retry. | 67 of 110 rejected answers were `confirmed` with no signal; a blind retry of the same prompt tends to repeat that. |
| D7 | Chromium launch arguments | Do not add `--disable-dev-shm-usage`: Playwright 1.62.1 already passes it by default (`playwright-core/lib/coreBundle.js`, the default Chromium switch list). Task 8 looks for the real cause. | Verified in the installed package. |

## Outcome of the accuracy checks (Task 9)

- Sending thinking disabled lowered accuracy. Confirmation agreed with the labels on 49 of 70 recordings with thinking disabled against 56 with the model default, and made 19 false confirmations against 11. Frame verification adjudicated 20 findings with thinking disabled against 54 with the default.
- Frame verification keeps the model's default thinking and gets at least 16,000 output tokens. Confirmation keeps the default thinking with a 16,000-token limit and a 300-second request timeout.
- The strict `submit_confirmation` tool and the structured-output variants did not improve accuracy and produced many invalid notes (24 to 27 of 60, against 0 for free text). A forced `tool_choice` disabled thinking in 69 of 69 answers. Confirmation stays on the free-text JSON answer, validated in code, with one blind retry.
- Follow-ups are tracked on #517.

```ts
/**
 * Handlers throw these after durably completing or rescheduling their own job,
 * to stop further work. The poller treats them as completed; traces and the
 * failed-job counter must agree. Matched by name so this module imports
 * nothing and tracing.ts never loads db.ts.
 */
const COMPLETION_SIGNALS: ReadonlySet<string> = new Set([
  'JobCompletedInTransaction',
  'JobRescheduledError',
]);

export function isJobCompletionSignal(err: unknown): err is Error {
  return err instanceof Error && COMPLETION_SIGNALS.has(err.name);
}
```

```ts
/** Health counters, exported for tests. */
export function jobCounters(): { processed: number; failed: number } {
  return { processed: jobsProcessed, failed: jobsFailed };
}

export async function processJob(job: ClaimedJob, signal: AbortSignal): Promise<void> {
  jobsInFlight += 1;
  try {
    await withJobTrace(job, () => processJobInner(job, signal));
  } catch (err: unknown) {
    // One seam for every thrown failure, so /health's jobs_failed agrees with
    // the dead letters the poller records. A completion signal is not a
    // failure: the poller records that job as completed.
    if (!isJobCompletionSignal(err)) jobsFailed++;
    lastJobAt = new Date().toISOString();
    throw err;
  } finally {
    jobsInFlight -= 1;
  }
}
```

```ts
    system: string;
    user: string;
    images?: NarrativeImages;
    signal?: AbortSignal;
    tool: Anthropic.Tool;
    rejected?: { assistant: Anthropic.ContentBlockParam[]; toolUseId: string; error: string };

    const messages: Anthropic.MessageParam[] = [
      { role: 'user', content: userContent(args.user, args.images) },
    ];
    if (args.rejected) {
      messages.push(
        // Verbatim, so thinking blocks the API requires on a thinking-on retry survive.
        { role: 'assistant', content: args.rejected.assistant },
        { role: 'user', content: [{ type: 'tool_result', tool_use_id: args.rejected.toolUseId, is_error: true, content: args.rejected.error }] },
      );
    }
    const response = await this.anthropic.messages.create({
      model: this.config.model,
      max_tokens: this.config.maxTokens,
      ...this.thinkingParam(),
      system: args.system,
      messages,
      tools: [args.tool],
      // Forced tool use is rejected while thinking is on, so only a
      // thinking-disabled client may force the call.
      // One answer per request: without disable_parallel_tool_use the model may
      // emit several conflicting calls.
      tool_choice: this.config.thinking === 'disabled'

        : { type: 'auto', disable_parallel_tool_use: true },

      (block): block is Anthropic.ToolUseBlock => block.type === 'tool_use',

      // its param type, keeping every field the API returned.
      assistant: response.content,
      ...usageOf(response.usage),
```

```ts
/** Internal only: customer surfaces read confirmed notes, and finalizeBatch
 * never turns an unavailable attempt into a check. The wording names why a
 * recording could not be checked so reasons can be counted with
 * `SELECT note,count(*) FROM friction_check_attempts WHERE outcome='unavailable' GROUP BY note`. */
export const UNAVAILABLE_NOTES: Record<UnavailableReason, string> = {
  recording_missing: 'Unavailable: recording missing or incomplete.',
  replay_crashed: 'Unavailable: replay browser crashed.',
  capture_failed: 'Unavailable: replay capture failed.',
  no_frames: 'Unavailable: replay produced no frames.',
  invalid_answer: 'Unavailable: confirmation answer failed validation.',
};
export function unavailableCheck(reason: UnavailableReason): ConfirmAnswer {
  return { outcome: 'unavailable', evidenceLines: [], signalIds: [], note: UNAVAILABLE_NOTES[reason], costToUser: null };
}

/** The recording's own IDs become enums, so the API refuses any other ID.
 * Lengths, the confirmed-needs-citations rule and provenance stay code checks:
 * strict schemas reject length and count bounds with a 400, and a schema
 * cannot make one field's requirement depend on another's value. */
export function confirmationTool(lineIds: readonly string[], signalIds: readonly string[]): Anthropic.Tool {
  const idList = (values: readonly string[], description: string) => ({
    type: 'array',
    description,
    // An empty enum is not a valid schema; validation rejects any ID instead.
    items: values.length ? { type: 'string', enum: [...values] } : { type: 'string' },
  });
  return {
    name: CONFIRM_TOOL_NAME,
    description: 'Record whether this recording shows the exact known problem.',
    strict: true,
    input_schema: seal({
      type: 'object',
      properties: {
        outcome: { type: 'string', enum: [...OUTCOMES] },
        evidenceLines: idList(lineIds, 'Timeline line IDs that support the outcome. confirmed needs at least one.'),
        signalIds: idList(signalIds, 'Supplied signal IDs that show this exact problem. confirmed needs at least one; when none matches, the outcome is refuted or inconclusive.'),
        note: {
          type: 'string',
          description: `Customer-facing, at most ${CONFIRM_NOTE_MAX_CODE_POINTS} characters: what the user did and what the screen showed. No line IDs, and never mention timelines, screenshots, frames or how anything was verified.`,
        },
        costToUser: { type: 'string', enum: [...COSTS] },
      },
      required: ['outcome', 'evidenceLines', 'signalIds', 'note', 'costToUser'],
    }),
  };
}

const codePoints = (text: string): number => [...text].length;
const isStringList = (value: unknown): value is string[] =>
  Array.isArray(value) && value.every((item) => typeof item === 'string');
const isOneOf = <T extends string>(values: readonly T[], value: unknown): value is T =>
  typeof value === 'string' && (values as readonly string[]).includes(value);

export function validateConfirmation(
  input: unknown,
  lines: ReadonlySet<string>,
  signals: ReadonlySet<string>,
): ConfirmAnswer | { rule: ConfirmInvalidRule } {
  if (!input || typeof input !== 'object' || Array.isArray(input)) return { rule: 'shape' };
  const raw = input as Record<string, unknown>;
  const { outcome, evidenceLines, signalIds, note, costToUser } = raw;
  if (
    !isOneOf(OUTCOMES, outcome) || !isStringList(evidenceLines) || !isStringList(signalIds) ||
    typeof note !== 'string' || !isOneOf(COSTS, costToUser)
  )
    return { rule: 'shape' };
  if (new Set(evidenceLines).size !== evidenceLines.length || new Set(signalIds).size !== signalIds.length)
    return { rule: 'duplicate_id' };
  if (evidenceLines.some((line) => !lines.has(line))) return { rule: 'unknown_line' };
  if (signalIds.some((id) => !signals.has(id))) return { rule: 'unknown_signal' };
  if (!note.trim()) return { rule: 'empty_note' };
  if (noteLeaksProvenance(note)) return { rule: 'note_mentions_provenance' };
  if (codePoints(note) > CONFIRM_NOTE_MAX_CODE_POINTS) return { rule: 'note_too_long' };
  if (outcome === 'confirmed' && !signalIds.length) return { rule: 'confirmed_without_signal' };
  if (outcome === 'confirmed' && !evidenceLines.length) return { rule: 'confirmed_without_line' };
  return { outcome, evidenceLines, signalIds, note, costToUser };
}
```

`ledger.mjs` wraps a client so every call, retries included, is recorded before any validation can hide it:

```js
import { appendFileSync, readFileSync, existsSync } from 'node:fs';
const LIMIT_USD = 40;
export function spentUsd(file) {
  if (!existsSync(file)) return 0;
  return readFileSync(file, 'utf8').trim().split('\n').filter(Boolean).map((line) => JSON.parse(line))
    .reduce((sum, call) => sum + (call.inputTokens * 2 + call.outputTokens * 10) / 1e6, 0);
}
export function estimateInputTokens(file) {
  if (!existsSync(file)) return 60_000;
  const calls = readFileSync(file, 'utf8').trim().split('\n').filter(Boolean).map((line) => JSON.parse(line));
  return calls.length ? Math.max(...calls.map((call) => call.inputTokens)) : 60_000;
}
export function ledgered(client, file, context, maxOutputTokens) {
  const log = async (method, args) => {
    // Reserve the worst case before dispatch: the largest input seen plus the whole output allowance.
    const worstCase = (estimateInputTokens(file) * 2 + maxOutputTokens * 10) / 1e6;
    if (spentUsd(file) + worstCase > LIMIT_USD) throw new Error(`spend limit $${LIMIT_USD} would be exceeded`);
    const started = Date.now();
    const reply = await client[method](args);
    const ctx = context();
    appendFileSync(file, JSON.stringify({
      ...ctx, method, retry: ctx.retry ?? Boolean(args.rejected), ms: Date.now() - started,
      stopReason: reply.stopReason, inputTokens: reply.inputTokens, outputTokens: reply.outputTokens,
    }) + '\n');
    return reply;
  };
  const wrapped = { modelName: client.modelName, complete: (args) => log('complete', args) };
  if (typeof client.callTool === 'function') wrapped.callTool = (args) => log('callTool', args);
  return wrapped;
}
```

Main's `confirmRead` retries blind, so Arm B sets `retry: true` in `context()` for the second call of a read; the ledger prefers a context flag over `args.rejected`.
