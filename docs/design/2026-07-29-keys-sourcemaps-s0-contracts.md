This appendix is the implementation boundary between ingestion, the browser SDK,
the Vite plugin, the worker, dashboard, and CLI. Field names, paths, limits, and
authorization behavior below are frozen for S1–S7. A change requires updating
this appendix, its fixtures, and every affected contract test in the same PR.

## 1. Shared HTTP rules

- All new JSON endpoints accept and return `application/json`.
- Successful timestamps are UTC RFC 3339 strings.
- UUID-valued IDs generated by the server are lowercase strings; key IDs use
  the base32 format in §3. Debug IDs use UUID text syntax but are raw hash bits:
  they do not carry RFC 9562 version or variant semantics. PostgreSQL `uuid`
  storage must round-trip all syntactically valid debug IDs without rewriting
  those bits.
- Unknown JSON fields are ignored unless this appendix says otherwise.
- Error responses preserve the existing human-readable `error` field and add a
  stable machine-readable `code`:

```json
{
  "error": "source map batch is incomplete",
  "code": "batch_incomplete"
}
```

- Responses never contain secret hashes, attempted credentials, source-map
  bytes, canonicalized map JSON, `sourcesContent`, or object-storage keys.
- `X-Request-Id` remains the correlation mechanism; it is not duplicated in
  response bodies.

Common errors:

| Status | Code | Meaning |
|---|---|---|
| 400 | `invalid_json` | Body is not valid JSON |
| 400 | `invalid_request` | A field is missing or invalid |
| 401 | `invalid_api_key` | Credential is missing, malformed, unknown, or revoked |
| 403 | `insufficient_scope` | Valid key presented to the wrong route family |
| 404 | `not_found` | Resource is absent or outside the caller's project |
| 409 | endpoint-specific | Request conflicts with immutable or lifecycle state |
| 413 | endpoint-specific | Declared or received data exceeds a frozen limit |
| 429 | `rate_limited` | Request-rate budget exceeded |
| 429 | `upload_budget_exceeded` | Source-map byte or concurrency budget exceeded |
| 500 | `internal_error` | Unexpected server failure |
| 503 | `storage_unavailable` | Source-map object storage is unavailable |

## 2. Authorization matrix

Authorization depends on the credential's database scope, never on its textual
prefix alone.

### 2.1 Public ingest key: `opslane_pk_`

Only these routes accept a key whose database scope is `ingest`:

```text
POST /api/v1/events
POST /api/v1/replays/init
POST /api/v1/replays/{replayID}/complete
POST /api/v1/replays/{replayID}/fail
POST /api/v1/sessions/init
POST /api/v1/sessions/{sessionID}/chunks/{seq}
```

`/events` retains the origin check that permits headerless server SDKs.
Replay/session routes retain the strict browser-origin check.

### 2.2 Secret source-map key: `opslane_sk_`

Only these routes accept a key whose database scope is `sourcemaps`:

```text
POST /api/v1/sourcemaps/batches
PUT  /api/v1/sourcemaps/batches/{batchID}/files/{debugID}
POST /api/v1/sourcemaps/batches/{batchID}/complete
```

There is no source-map GET route. The old
`POST /api/v1/sourcemaps` route is removed and returns 404; there is no
compatibility shim.

### 2.4 Other principals

| Principal | Routes |
|---|---|
| Poll token | `GET /api/v1/agent/poll/{sessionID}` |
| Internal service token | `GET /internal/v1/projects/{projectID}/sessions/{sessionID}/chunks/{seq}` |
| GitHub HMAC | `POST /api/v1/github/webhook` |
| No router middleware | health, metrics, auth/OAuth protocol routes, agent setup/auth callbacks, GitHub webhook, dashboard static files |

Agent setup is unauthenticated and creates the poll secret. Poll requests send
that secret in `X-Opslane-Poll-Token`; the server compares its stored hash in
constant time. A missing, malformed, unknown, or incorrect poll token returns
404 so the endpoint does not disclose whether the session exists. The
onboarding self-test result travels through the existing poll response; no
public-key read endpoint is retained for it.

“No router middleware” does not mean “no proof.” Refresh, reset, email
verification, OAuth/PKCE exchange, callbacks, and the GitHub webhook keep their
existing cookie, code, state, origin, PKCE, or HMAC checks inside their
handlers. They are excluded from the customer-key cross-product because S0 does
not change those protocol contracts. `/health` is intentionally public.
`/metrics` has no application authentication and must be network-restricted by
the deployment.

### 2.5 CORS

Permissive SDK CORS applies only to exact `/api/v1/events`,
`/api/v1/replays/...`, and `/api/v1/sessions/...` routes. Source-map upload is
server-to-server traffic and receives no permissive browser CORS. Session
source-map routes use the credentialed dashboard origin. Prefix matching must
not classify lookalike paths as SDK routes.

## 3. Project keys

### 3.1 Raw formats

```text
opslane_pk_<key_id>_<token>
opslane_sk_<key_id>_<secret>
```

- `key_id`: 128 random bits, RFC 4648 lowercase base32 without padding,
  26 characters matching `^[a-z2-7]{26}$`.
- `token` / `secret`: 256 random bits, base64url without padding,
  43 characters matching `^[A-Za-z0-9_-]{43}$`.
- Only the SHA-256 digest of the token/secret is stored.
- `key_id`, prefix, scope, and lifecycle metadata are not secret.
- A secret key is returned only by its creation response.

Authentication parses the prefix and `key_id`, loads that one row, verifies the
database scope matches the prefix, and compares the supplied secret digest in
constant time.

### 3.2 Lifecycle invariants

- Creating a key never changes another key.
- There is no product-level active-key count limit.
- Revocation is an explicit, authenticated request naming one exact `key_id`.
- Revocation is immediate and irreversible; the row remains for audit.
- Age, inactivity, rotation, key creation, and background cleanup never revoke
  a key.
- Explicit deletion of the parent project invalidates all of its keys.
- Creation and request rate limits are abuse controls, not key-count limits.
- `last_used_at` and rejected-attempt timestamps are coalesced to at most one
  database write per key per five minutes.
- Wrong-scope attempts made with a public key do not create rejected-upload
  warnings.

### 3.3 Persistence

```sql
CREATE TABLE project_api_keys (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  key_id TEXT NOT NULL UNIQUE
    CHECK (key_id ~ '^[a-z2-7]{26}$'),
  project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  scope TEXT NOT NULL CHECK (scope IN ('ingest', 'sourcemaps')),
  token_prefix TEXT NOT NULL
    CHECK (
      (scope = 'ingest' AND token_prefix = 'opslane_pk') OR
      (scope = 'sourcemaps' AND token_prefix = 'opslane_sk')
    ),
  secret_hash TEXT NOT NULL UNIQUE
    CHECK (secret_hash ~ '^[0-9a-f]{64}$'),
  label TEXT NOT NULL
    CHECK (label = btrim(label) AND char_length(label) BETWEEN 1 AND 100),
  created_by_user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_used_at TIMESTAMPTZ,
  last_rejected_at TIMESTAMPTZ,
  last_rejected_reason TEXT
    CHECK (last_rejected_reason IN ('invalid_secret', 'revoked')),
  revoked_at TIMESTAMPTZ,
  revoked_by_user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  UNIQUE (id, project_id),
  CHECK (revoked_at IS NOT NULL OR revoked_by_user_id IS NULL),
  CHECK (
    (last_rejected_at IS NULL AND last_rejected_reason IS NULL) OR
    (last_rejected_at IS NOT NULL AND last_rejected_reason IS NOT NULL)
  )
);

CREATE INDEX idx_project_api_keys_project_created
  ON project_api_keys(project_id, created_at DESC, id DESC);

CREATE INDEX idx_project_api_keys_project_active_scope
  ON project_api_keys(project_id, scope)
  WHERE revoked_at IS NULL;
```

There is deliberately no partial unique index restricting active keys.

### 3.4 Create

```http
POST /api/v1/projects/{projectID}/api-keys
Content-Type: application/json

{
  "scope": "sourcemaps",
  "label": "Vercel production"

```

`scope` is `ingest` or `sourcemaps`; `label` is trimmed UTF-8 text containing

```json
{
```

### 3.5 List

```http
GET /api/v1/projects/{projectID}/api-keys?limit=50&cursor=<opaque>
```

`200`:

```json
{
  "keys": [
    {
      "key_id": "mzxw6ytboi3damrrgi3tknzxgq",
      "scope": "sourcemaps",
      "label": "Vercel production",
      "status": "active",
      "created_at": "2026-07-29T20:00:00Z",
      "last_used_at": "2026-07-29T20:15:00Z",
      "last_rejected_at": null,
      "last_rejected_reason": null,
      "revoked_at": null
    }
  ],
  "next_cursor": null
}
```

`limit` defaults to 50 and must be 1–100. Results are ordered by
`created_at DESC, id DESC`; revoked rows remain visible. `cursor` is the
base64url-without-padding encoding of the UTF-8 JSON object
`{"created_at":"<RFC3339-microseconds>","id":"<uuid>"}` for the final row from
the previous page. The timestamp is UTC with the database's full stored
microsecond precision, formatted as `2006-01-02T15:04:05.999999Z`. The server
validates both fields and applies the strict tuple predicate
`(created_at, id) < (cursor.created_at, cursor.id)`. Clients treat the value as
opaque. `next_cursor` is null when no later page exists.

### 3.7 Explicit revoke

```http
POST /api/v1/projects/{projectID}/api-keys/{keyID}/revoke
Content-Type: application/json

```

Success returns the metadata object with `status: "revoked"` and `revoked_at`

No individual-key `DELETE` endpoint exists.

## 4. Default environment after project-scoped keys

Environment remains stored as an environment row, but it is no longer selected
by the key.

```sql
ALTER TABLE environments
  ADD CONSTRAINT environments_id_project_unique UNIQUE (id, project_id);

ALTER TABLE projects
  ADD COLUMN default_environment_id UUID;

ALTER TABLE projects
  ADD CONSTRAINT projects_default_environment_same_project
  FOREIGN KEY (default_environment_id, id)
  REFERENCES environments(id, project_id)
  DEFERRABLE INITIALLY DEFERRED;
```

Project creation is one transaction: create project, create its `production`
environment, set `default_environment_id`. After internal data is backfilled,
`default_environment_id` becomes `NOT NULL`.

Every ingest request starts with the project default. If an event/session
payload sends an environment label matching a pre-created environment in that
project, that row is used. Unknown labels do not create rows; they fall back to
the default, while the normalized submitted label is retained for diagnostics.

```sql
ALTER TABLE error_events
  ADD COLUMN submitted_environment TEXT;
```

## 5. Event `debug_meta` wire contract

SDK release `2.1.0` adds one optional top-level field:

```json
{
  "commit_sha": "e60b4d1e113538d40f09e31717e949aaa08659f8",
  "debug_meta": {
    "images": [
      {
        "type": "sourcemap",
        "code_file": "https://app.example.com/assets/index-BpTz.js",
        "debug_id": "01234567-89ab-cdef-0123-456789abcdef"
      }
    ]
  }
}
```

Shared TypeScript shape:

```ts
interface DebugMeta {
  images?: DebugImage[];
}

interface DebugImage {
  type: 'sourcemap';
  code_file: string;
  debug_id: string;
}

interface ErrorEventPayload {
  commit_sha?: string;
  debug_meta?: DebugMeta;
}
```

Rules:

- `commit_sha` is optional and, when present, is a lowercase Git object ID of
  exactly 40 or 64 hexadecimal characters. The build plugin detects and injects
  it; `release` remains separate display metadata. An invalid optional
  `commit_sha` is discarded and counted, never grounds for rejecting the event.
- `debug_meta` and `images` are optional; omission and an empty array are
  equivalent.
- The SDK attaches only entries matching files in the captured stack, not every
  loaded chunk.
- At most 64 valid images are retained: the first 64 unique images in captured
  stack order.
- `code_file` is an opaque identifier of 1–4096 UTF-8 bytes with no NUL or
  ASCII control characters. Opslane never fetches it.
- `debug_id` is lowercase and UUID-shaped:
  `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`.
- Exact `(code_file, debug_id)` duplicates collapse.
- If one `code_file` claims conflicting IDs, every entry for that file is
  discarded as ambiguous.
- Unknown members are ignored.
- Malformed optional metadata never rejects the error event. Valid entries are
  retained; invalid/excess entries are discarded and counted in validation
  metrics.
- The worker joins parsed stack frames to metadata using exact `code_file`
  first. There is no basename fallback.

Persistence:

```sql
ALTER TABLE error_events
  ADD COLUMN debug_meta JSONB NOT NULL DEFAULT '{"images":[]}'::jsonb
    CHECK (jsonb_typeof(debug_meta) = 'object'),
  ADD COLUMN commit_sha TEXT
    CHECK (commit_sha IS NULL OR commit_sha ~ '^(?:[0-9a-f]{40}|[0-9a-f]{64})$');
```

Frozen fixtures:

```text
test-fixtures/wire/events/v2.1.0-minimal.json  # debug_meta omitted
test-fixtures/wire/events/v2.1.0-full.json     # one sourcemap image plus the exact 40-character commit_sha shown above
```

Existing fixtures are never edited.

## 6. Debug-ID algorithm and accepted map shape

The algorithm is identical in TypeScript and Go:

```text
1. Strictly parse the UTF-8 source-map JSON.
2. Require a root object; reject BOM, invalid UTF-8, duplicate object keys,
   and nesting deeper than 64.
3. Remove only the root-level "debugId" member.
4. Serialize the remaining value with RFC 8785 JSON Canonicalization Scheme.
5. digest = SHA-256(UTF-8(canonical JSON)).
6. Take digest bytes 0..15 and format them directly as lowercase
   8-4-4-4-12 hexadecimal groups. No UUID version/variant bits are rewritten.
7. Store the full 32-byte digest separately as content_sha256.
```

The map is valid only when:

- root `version` is exactly `3`;
- it is a non-indexed map (`sections` is absent);
- `sources`, `names`, and `mappings` have their ECMA-426 types;
- `sourcesContent` is present, is an array, has the same length as `sources`,
  and every entry is a string corresponding to the source at the same index;
- the uploaded root `debugId` equals the manifest/path `debug_id`;
- canonical size is at most 100 MiB.

All root extensions participate in the hash; only root `debugId` is removed.
Arrays retain their order and object keys are recursively canonicalized.

The plugin stamps the resulting ID into the generated JS
(`//# debugId=<id>`), into the root map `debugId`, and into the runtime debug
registry. The server recomputes it from the received map. Different content
whose computed ID does not equal the claimed ID returns
`409 debug_id_mismatch`. A matching 128-bit ID whose full 256-bit digest differs
from an existing project artifact returns `409 debug_id_conflict`. Identical
canonical content is idempotent.

Map parsing/canonicalization uses bounded temporary storage and a global upload
semaphore. The 100 MiB limit must not be implemented with an unrestricted
`io.ReadAll` path.

### 6.1 Golden vectors

These values are literal cross-language contract vectors. `canonical` is shown

### 6.2 PostgreSQL storage vector

Debug IDs deliberately preserve raw hash bits instead of rewriting UUID version
or variant positions. PostgreSQL's `uuid` type accepts that syntax and preserves
all 128 bits. This was verified against the repository's running PostgreSQL
16.14 service:

```sql
SELECT
  '158399f3-1dad-1386-35b2-98c34317d52e'::uuid::text =
  '158399f3-1dad-1386-35b2-98c34317d52e';
-- true
```

The S2 migration test inserts this value through both
`sourcemap_batch_files.debug_id` and `sourcemap_files.debug_id`, reads it back,
and compares the exact text. This protects the storage assumption across future
PostgreSQL upgrades.

## 7. Source-map batch API

### 7.1 Create a batch

```http
POST /api/v1/sourcemaps/batches
X-API-Key: opslane_sk_...
Idempotency-Key: <request-uuid>
Content-Type: application/json

{
  "commit_sha": "e60b4d1e113538d40f09e31717e949aaa08659f8",
  "release": "web@e60b4d1",
  "probe": false,
  "files": [
    {
      "debug_id": "01234567-89ab-cdef-0123-456789abcdef",
      "code_file": "assets/index-BpTz.js",
      "size_bytes": 812340
    }
  ]
}
```

Rules:

- Body: at most 256 KiB.
- `Idempotency-Key`: required UUID. A semantically identical retry returns the
  existing batch with `200`; the same key with a different normalized manifest
  returns `409 idempotency_conflict`.
- Manifest normalization applies defaults, sorts `files` by `debug_id`, and
  serializes the normalized object with RFC 8785. Only recognized fields are
  retained; absent `commit_sha` and `release` become `null`; absent `probe`
  becomes `false`; every file is represented by exactly `debug_id`,
  `code_file`, and integer `size_bytes`. `manifest_sha256` is SHA-256 of those
  bytes. Submitted field and file order therefore do not change idempotency.
- Batch rows, including their idempotency keys, remain for audit in v1.
- `files`: 1–500 entries with unique `debug_id` values.
- `code_file`: 1–4096 UTF-8 bytes, no control characters.
- `size_bytes`: integer 1–104857600 (100 MiB).
- Sum of `size_bytes`: at most 1073741824 (1 GiB).
- `commit_sha`: optional lowercase Git object ID of exactly 40 or 64 hex
  characters.
- `release`: optional display text, at most 200 UTF-8 bytes.
- `probe`: optional, defaults to `false`.
- Project comes from the sk. No `project_id` is accepted in v1.
- Batch creation is limited to 20 requests/minute per project. Idempotent
  retries count toward the request limit.

New batch returns `201`; idempotent retry returns `200`:

```json
{
  "batch_id": "38aed86c-67d0-49ae-90ec-a87e383a8874",
  "status": "pending",
  "expected_files": 1,
  "expected_bytes": 812340,
  "expires_at": "2026-07-29T22:00:00Z"
}
```

Manifest errors:

| Status | Code |
|---|---|
| 400 | `invalid_manifest` |
| 400 | `duplicate_debug_id` |
| 409 | `idempotency_conflict` |
| 413 | `manifest_too_large` |
| 413 | `too_many_files` |
| 413 | `file_too_large` |
| 413 | `batch_too_large` |
| 429 | `rate_limited` |

### 7.2 Upload one file

```http
PUT /api/v1/sourcemaps/batches/{batchID}/files/{debugID}
X-API-Key: opslane_sk_...
Content-Type: application/json
Content-Length: 812340

<raw stamped .map bytes>
```

- `Content-Length` is required and must equal the manifest declaration.
- `Content-Encoding` is unsupported in v1.
- Unknown and cross-project batches both return 404.
- The debug ID must be declared in this batch.
- At most 10 file PUTs may run concurrently for one batch. Per-project
  concurrency is capped at 20 active PUTs. File PUTs are limited to 600
  requests/minute per project. Separately, a project may receive at most 2 GiB
  of source-map request bodies in a rolling 10-minute window, with at most
  1 GiB of source-map request bodies in flight. Request-rate responses use
  `429 rate_limited`; byte/concurrency responses use
  `429 upload_budget_exceeded`. Both include `Retry-After` and leave batch
  state unchanged.
- All request, byte, and concurrency limits are cluster-wide, not per
  ingestion replica. PostgreSQL stores rolling request/byte buckets and active
  upload leases. A PUT reserves its declared `Content-Length` and one
  concurrency slot before reading the body, renews the lease while active, and
  releases it on completion; abandoned leases expire after five minutes.
- The server validates, canonicalizes, and verifies the ID before staging the
  artifact.
- A new staged artifact returns `201`; identical retry/reuse returns `200`.
- For a completed batch, an undeclared path returns
  `409 debug_id_not_declared`. A declared file whose canonical digest matches
  the stored manifest row returns idempotent `200 already_present`; any other
  body for that declared path returns `409 batch_already_complete`. This
  lifecycle check takes precedence over reclassifying the new body as a map
  mismatch.

```json
{
  "batch_id": "38aed86c-67d0-49ae-90ec-a87e383a8874",
  "debug_id": "01234567-89ab-cdef-0123-456789abcdef",
  "status": "stored",
  "received_bytes": 812340
}
```

`status` is `stored` or `already_present`.

File errors:

|---|---|
| 404 | `batch_not_found` |
| 410 | `batch_expired` |
| 409 | `batch_already_complete` |
| 409 | `debug_id_not_declared` |
| 411 | `length_required` |
| 409 | `size_mismatch` |
| 415 | `unsupported_media_type` |
| 400 | `invalid_source_map` |
| 409 | `debug_id_mismatch` |

### 7.3 Complete

```http
POST /api/v1/sourcemaps/batches/{batchID}/complete
X-API-Key: opslane_sk_...
Content-Type: application/json

{}
```

First completion and identical repeats return `200`:

```json
{
  "batch_id": "38aed86c-67d0-49ae-90ec-a87e383a8874",
  "status": "complete",
  "file_count": 1,
  "byte_count": 812340,
  "commit_sha": "e60b4d1e113538d40f09e31717e949aaa08659f8",
  "release": "web@e60b4d1",
  "probe": false,
  "completed_at": "2026-07-29T21:05:00Z"
}
```

Incomplete returns `409` without listing private paths or map data:

```json
{
  "error": "source map batch is incomplete",
  "code": "batch_incomplete",
  "expected_files": 14,
  "received_files": 9
}
```

Only artifacts attached to at least one completed batch are resolvable. Probe
batches are resolvable by the verification endpoint but excluded from project
health/status summaries.

Completion is limited to 60 requests/minute per project. It does not consume
the source-map byte budget: the bytes are already staged, and completion must
remain available to make them usable.

Completion takes one lease on the batch, not on individual maps. Two different
batches never wait on one another merely because they contain the same map:
both may copy the same verified canonical bytes to the same digest-addressed
object, and the final database transaction links both batches to one project
artifact. If another request is already completing this exact batch, the
server waits up to five seconds. If the first request is still live, the
contender returns `409 batch_completion_in_progress` with `Retry-After: 2`.
Retries are idempotent and resume after the owning request finishes or its
lease expires.

Completion errors:

| Status | Code |
|---|---|
| 400 | `invalid_request` |
| 404 | `batch_not_found` |
| 410 | `batch_expired` |
| 409 | `batch_incomplete` |
| 409 | `debug_id_conflict` |
| 409 | `batch_completion_in_progress` |
| 429 | `rate_limited` |
| 503 | `storage_unavailable` |

An already-completed retry returns its original `200` receipt.

### 7.4 Plugin-side map custody

The Vite adapter never writes readable maps into the deploy output or preserves
them across processes. During `generateBundle` it removes map assets from the
Rollup output and uploads them before the build process exits. To keep memory
bounded, temporary spill files are encrypted with AES-256-GCM using one random
per-build key held only in process memory. Each file uses a unique 96-bit nonce,
an authenticated tag, a random filename, directory mode 0700, and file mode
0600 beneath the OS temporary directory, outside the repository and Vite
`outDir`.

The plugin retries from memory/encrypted spill files only during the current
build. A completion receipt deletes them. A final upload failure also
best-effort deletes them and logs no path or map content; a crash may leave only
unreadable ciphertext because the key dies with the process. The next build
regenerates the maps. The plugin does not perform cross-process startup cleanup
in v1, because it cannot safely distinguish an orphan from another live build;
OS temporary-storage cleanup owns eventual removal of crash remnants. This is
the frozen meaning of “upload before deletion”: source remains available
through the upload attempt but can never ride a green deploy or remain readable
on disk afterward.

## 8. Source-map persistence and object lifecycle

### 8.1 Tables

```sql
    CHECK (expected_file_count BETWEEN 1 AND 500),

  expires_at TIMESTAMPTZ NOT NULL,

CREATE OR REPLACE FUNCTION prevent_sourcemap_file_identity_update()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF ROW(
    NEW.project_id,
    NEW.debug_id,
    NEW.content_sha256,
    NEW.size_bytes,
    NEW.object_key,
    NEW.created_at
  ) IS DISTINCT FROM ROW(

    OLD.debug_id,
    OLD.content_sha256,

CREATE TRIGGER trg_sourcemap_file_identity_immutable

FOR EACH ROW

```

`raw_sha256` is SHA-256 of the exact uploaded request bytes.
`content_sha256` is SHA-256 of RFC-8785 canonical content after removing the
root `debugId`. The PUT computes both digests and `canonical_size_bytes`, then
writes the deterministic UTF-8 canonical JSON—not the raw request—to staging.
The canonical object therefore omits root `debugId`; lookup already supplies
the ID. `sourcemap_files.size_bytes` is the canonical byte length. Two uploads
with the same `content_sha256` produce byte-identical staging and canonical
objects even when their raw whitespace, key order, or size differs.

### 8.2 Object keys

Only server-generated UUIDs and server-computed lowercase SHA-256 values enter
object paths:

```text
staging:
sourcemaps/v1/projects/{project_uuid}/batches/{batch_uuid}/{debug_uuid}.map

canonical:
sourcemaps/v1/projects/{project_uuid}/maps/{content_sha256_lower_hex}.map
```

Release names, source paths, labels, and other client strings never enter an
object key. The canonical digest is computed from the verified canonical bytes;
the caller never supplies it as an object-key component. Object keys are never
returned to clients. Canonical object writes must be atomic at one key and
strongly readable after success, as provided by the supported S3/MinIO storage
boundary.

### 8.3 Lifecycle

1. Batch creation inserts the batch and all manifest rows transactionally.
2. PUT persists the raw and canonical digests, raw received size, and canonical
   size. If an activated project artifact has the same debug ID and full
   canonical digest, the manifest row becomes `linked` immediately and no
   staging object is written. A different full digest for that debug ID returns
   `debug_id_conflict`. Otherwise the verified map is written to its batch
   staging key and the deterministic canonical bytes become `staged`. The first
   transition out of `pending` increments batch received counts in the same
   transaction; retries never increment them again. PUT never creates a
   project-wide reservation.
3. Completion atomically changes one fully received `pending` batch to
   `completing` and takes a five-minute lease before touching object storage.
   The lease exists only to keep expiry cleanup away from this batch and to
   make an abandoned completion reclaimable. The request retains the exact
   database-generated `completion_claimed_at`; reclaiming a lease replaces that
   value, so it also identifies the current batch claim without a generation
   counter. There is no per-map reservation, lease, or ownership state.
4. For every `staged` manifest row, completion first checks the project map
   table. An existing row with the same debug ID and full digest needs no copy.
   An existing row with a different full digest returns `debug_id_conflict`.
   Otherwise completion copies the verified canonical staging bytes to
   `maps/{content_sha256_lower_hex}.map`. Different batches may copy the same
   object concurrently: equal full digests mean byte-identical canonical
   content, so repeating that atomic write is harmless. Different full digests
   use different object keys and cannot overwrite one another.
5. After every required object write succeeds, one database transaction locks
   and revalidates the batch, requires `status = 'completing'`, a live lease,
   the exact `completion_claimed_at` retained by this request, and exact
   received counts, then activates the whole batch:
   - insert each missing `sourcemap_files` row;
   - on `(project_id, debug_id)` conflict, reuse the existing row when its full
     digest and canonical size match;
   - abort the whole transaction with `debug_id_conflict` when the full digest
     differs;
   - link every manifest row and mark the batch `complete`;
   - set `completed_at` and clear both completion-claim timestamps.
   A `sourcemap_files` row therefore means the object was already written and
   activated; there is no intermediate map state.
6. The transaction in step 5 is the only visibility point. A crash before it
   may leave an unreferenced digest object but exposes no map or partial batch.
   A retry repeats the copies safely. A crash after commit returns the original
   receipt on retry. If an old completion resumes after its claim was
   reclaimed, the batch was completed, or the batch was atomically expired,
   its final transaction changes zero rows.
7. Staging objects are removed after successful completion. A pending batch
   expires after one hour. A `completing` batch is never swept under a live
   lease; after expiry, a reclaimer either resumes it or atomically changes it
   to `expired`, clears the claim, and removes its staging objects.
8. V1 does not eagerly delete an unreferenced canonical digest object left by
   a crashed or conflicting completion, because another completion may be
   about to activate the same digest. Such an object is invisible to workers
   and is removed by project-prefix deletion. Active-project orphan collection
   is a later storage optimization, not part of the correctness contract.
9. Workers select maps only through manifest rows linked to a `complete`
   batch. An object that exists without that database path is unreadable.
10. Project deletion first inserts `sourcemap_project_tombstones` in the same
    database transaction that deletes the project and its dependent database
    rows. That includes every `error_events.stack_trace_resolved` cache: the
    bounded `source_snippet` values are copies of customer source and are
    deleted with their error events, not left behind after map deletion. The
    cleanup worker takes a five-minute `storage_sweep_lease_expires_at`; an
    expired claim is reclaimable. It retries removal of
    `sourcemaps/v1/projects/{project_uuid}/` until storage confirms the prefix
    is empty, then sets `storage_swept_at`. Database cascades alone are not
    considered deletion of customer source. Backups containing either maps or
    cached snippets expire under the platform's documented backup-retention
    policy.

Storage is never deduplicated across projects.

## 9. Verification endpoint

```http
POST /api/v1/projects/{projectID}/sourcemaps/verify
Authorization: Bearer <session>
Content-Type: application/json

{
  "batch_id": "38aed86c-67d0-49ae-90ec-a87e383a8874",
  "debug_id": "01234567-89ab-cdef-0123-456789abcdef",
  "generated_line": 1,
  "generated_column": 846
}
```

- The batch must be complete and belong to the project.
- The debug ID must belong to that batch.
- `generated_line` is 1-based, integer 1–2147483647.
- `generated_column` is 0-based, integer 0–2147483647.
- The endpoint is limited to 30 requests/minute per user/project and every call
  is audit logged. Audit fields are user, project, batch, debug ID, generated
  line/column, result code, and timestamp—never the resolved source path or
  source text.

Success, `200`:

```json
{
  "status": "resolved",
  "debug_id": "01234567-89ab-cdef-0123-456789abcdef",
  "generated": {
    "line": 1,
    "column": 846
  },
  "original": {
    "file": "src/App.tsx",
    "line": 42,
    "column": 10,
    "name": "render"
  }
}
```

Original line is 1-based, original column is 0-based, and `name` is nullable.
No source snippet is returned. Repeated calls could enumerate positions, so the
protection is honest: session/project authorization, batch binding, rate
limiting, audit logs, and no source text—not a claim that enumeration is
impossible.

|---|---|
| 400 | `invalid_request` |
| 404 | `batch_not_found` |
| 404 | `map_not_found` |
| 422 | `position_not_mapped` |

## 10. Resolution persistence

```sql
ALTER TABLE error_events
  ADD COLUMN resolution_status TEXT
  CHECK (resolution_status IN (
    'resolved',
    'partial',
    'no_debug_ids',
    'map_not_found',
    'invalid_map',
    'resolution_failed'
  )),
  ADD COLUMN resolution_app_frame_count INTEGER NOT NULL DEFAULT 0
    CHECK (resolution_app_frame_count >= 0),
  ADD COLUMN resolution_resolved_frame_count INTEGER NOT NULL DEFAULT 0
    CHECK (
      resolution_resolved_frame_count >= 0 AND
      resolution_resolved_frame_count <= resolution_app_frame_count
    ),
  ADD COLUMN resolution_problem TEXT
    CHECK (resolution_problem IN (
      'no_debug_ids',
      'map_not_found',
      'invalid_map',
      'resolution_failed'
    )),
  ADD CONSTRAINT error_events_resolution_consistent CHECK (
    (resolution_status IS NULL AND resolution_problem IS NULL)
    OR
    (
      resolution_status = 'resolved'
      AND resolution_app_frame_count > 0
      AND resolution_resolved_frame_count = resolution_app_frame_count
      AND resolution_problem IS NULL
    )
    OR
    (
      resolution_status = 'partial'
      AND resolution_resolved_frame_count > 0
      AND resolution_resolved_frame_count < resolution_app_frame_count
      AND resolution_problem IS NOT NULL
    )
    OR
    (
      resolution_status = 'no_debug_ids'
      AND resolution_resolved_frame_count = 0
      AND (
        (resolution_app_frame_count = 0 AND resolution_problem IS NULL)
        OR
        (resolution_app_frame_count > 0 AND resolution_problem = 'no_debug_ids')
      )
    )
    OR
    (
      resolution_status IN ('map_not_found', 'invalid_map', 'resolution_failed')
      AND resolution_resolved_frame_count = 0
      AND resolution_problem = resolution_status
    )
  );

CREATE INDEX idx_error_events_resolution_problem
  ON error_events(project_id, created_at DESC)
  WHERE resolution_problem IS NOT NULL;
```

`resolution_status` is nullable until the worker attempts JavaScript
symbolication. `stack_trace_resolved` remains the JSONB cache and, when set,
contains:

```json
{
  "version": 1,
  "frames": [
    {
      "generated_file": "https://app.example.com/assets/index-BpTz.js",
      "generated_line": 1,
      "generated_column": 846,
      "debug_id": "01234567-89ab-cdef-0123-456789abcdef",
      "original_file": "src/App.tsx",
      "original_line": 42,
      "original_column": 10,
      "function": "render",
      "source_snippet": "..."
    }
  ]
}
```

Generated line is 1-based. Browser stack columns are converted to the
0-based convention expected by the source-map consumer before lookup. Original
line is 1-based and original column is 0-based. `function` and
`source_snippet` are nullable.

When present, `source_snippet` contains the original line plus at most two
preceding and two following lines, joined with `\n`. It is at most 8192 UTF-8
bytes and must retain the failing line. If clipping is required, remove outer
context first, then clip the failing line around `original_column` without
splitting a UTF-8 code point. The same bounded value is rendered in the issue
and supplied to the configured model provider; neither path reloads or sends
the full map.

`stack_trace_resolved` is a second storage location for customer source, not
mere derived metadata. It contains only the bounded excerpts needed by the
issue and fix-agent flows, but it receives the same tenant isolation, access
logging, deletion, and backup-retention treatment as the full map. Project
deletion removes these cached excerpts with `error_events` as part of the
database deletion transaction; the object-prefix sweep handles the full maps.

`resolution_status` describes the overall result. `resolution_problem`
describes the highest-priority cause among unresolved application frames and
therefore remains populated for `partial` events. Problem priority is
`resolution_failed`, then `invalid_map`, then `map_not_found`, then
`no_debug_ids`.

Status decision order:

1. Zero application frames: `no_debug_ids` with `resolution_problem = null`;
   this is non-actionable and UI copy says there are no debuggable application
   frames.
2. Every application frame resolved and the count is greater than zero:
   `resolved` with no problem.
3. At least one frame resolved and at least one application frame did not:
   `partial`, with the highest-priority unresolved-frame problem.
4. Zero frames resolved: use the highest-priority problem as both
   `resolution_status` and `resolution_problem`. A frame with no usable debug
   ID contributes `no_debug_ids`; a usable ID with no available map contributes
   `map_not_found`; a matching artifact that fails integrity/parsing contributes
   `invalid_map`; storage/internal failure or an unmapped generated position
   contributes `resolution_failed`.

Issue-level UI reads these fields from the issue's current sample event. A later
event is processed normally; old events are not reprocessed in v1.

```json
    "completed_at": "2026-07-29T21:05:00Z",

```

All nested values are nullable. Probe batches are excluded.
`latest_resolution_problem` is derived from the current sample events of active
issues, not from superseded historical occurrences.

`state` is:

- `no_uploads`: no completed non-probe batch and no later actionable signal;
- `healthy`: a completed non-probe batch exists and neither a rejected attempt
  nor resolution problem is newer;
- `action_required`: a rejected source-map-key attempt or any sample event with
  non-null `resolution_problem` is newer than the last successful non-probe
  batch.

There is no arbitrary age-based “stale” timer. The endpoint returns observed
facts and only asks for action when the system has observed a failure.

## 12. Commit provenance

`commit_sha` is supplied by an authenticated build key, but it is still a
client assertion—not cryptographic proof of which commit produced a map.

The worker may check out a batch commit only when:

1. the event's optional `commit_sha` exactly equals a completed batch's
   `commit_sha`;
2. that completed batch contains every debug ID used to resolve the event's
   application frames;
3. the commit exists in the configured repository.

Otherwise symbolication still uses the map, but repository checkout falls back
to the existing default-branch behavior and records that provenance was
unverified. `release` remains display metadata and never selects a commit.

## 13. S0 acceptance tests

S0 freezes the following fixture specifications; the fixture files and tests
land with their owning implementation slices.

1. Route matrix fixture: every production route crossed with session, pk, sk,
   poll/internal where applicable, and no credential. CORS cases prove the six
   ingest routes are permissive, source-map batch/status/verify routes are not,
   and lookalike prefixes receive no SDK CORS.
2. Key lifecycle fixture: create A, create B, both authenticate; revoke A,
   A fails and B remains active; creating C revokes nothing.
3. Key response fixtures: create/list/rename/revoke shapes above; pagination
   proves stable `(created_at, id)` traversal across active and revoked keys.
4. Wire fixtures:
   `v2.1.0-minimal.json` and `v2.1.0-full.json`.
5. Debug-ID vectors: canonical map input, expected SHA-256, expected debug ID,
   stamped-map rehash stability, poisoned-map mismatch, and a real PostgreSQL
   round trip through both debug-ID columns. The database vector includes
   `158399f3-1dad-1386-35b2-98c34317d52e`, whose raw hash bits do not encode an
   RFC UUID variant, and proves PostgreSQL stores and returns it unchanged.
6. Batch fixtures: create, idempotent create, file stored/reused, incomplete
   completion, complete receipt, expired batch, exact request/byte limits, and
   completion not consuming the byte budget. A multi-replica test proves the
   limits are cluster-wide.
7. Tenant isolation: the same debug ID in two projects creates two objects;
   neither project's key/session can reference the other's batch or map.
8. Custody: source content and object keys never appear in responses or logs;
   project deletion removes object prefixes and every database copy of source,
   including `stack_trace_resolved.frames[*].source_snippet`; backup-retention
   fixtures cover both storage locations. Snippet vectors prove the failing
   line survives, context never exceeds five lines, UTF-8 remains valid, and
   encoded size never exceeds 8192 bytes.
9. Verification vector: a real generated position resolves to the expected
   file, 1-based line, 0-based column, and nullable name.
10. Status fixtures: `no_uploads`, `healthy`, and `action_required`, with probe
    batches excluded and a `partial` event retaining its actionable problem.
11. Concurrency fixtures: two API replicas complete batches containing the same
    vendor map and both return `200`, with one digest-addressed object, one
    `sourcemap_files` row, and two batch links. A database-seeded synthetic
    case supplies a different full digest for the same 128-bit ID and proves it
    conflicts without changing the winner; producing that collision through
    the public hash algorithm is intentionally infeasible. A crash after object
    copy but before database activation leaves the map unresolvable and retry
    completes it; a crash after commit returns the original receipt. A live
    batch claim blocks expiry cleanup, a reclaimed `completion_claimed_at` and
    an atomically expired batch both reject a stale final transaction, and a
    failed final transaction exposes no partial batch. An expired
    project-deletion sweep claim remains reclaimable.
12. Plugin-custody fixtures: no `.map` enters Rollup output; spill files are
    authenticated ciphertext outside the repository and `outDir`; a receipt or
    handled failure deletes them; a simulated crash leaves ciphertext that a
    new process cannot decrypt; a second concurrent build never reads or
    deletes the first build's spill directory.
