# Session bucketing: competitive notes on frustration signals, grouping keys, and URL normalization

Date: 2026-08-09
Location: `docs/research/`. The repo already keeps dated research notes here (`2026-08-04-environment-models.md`, `2026-08-04-sourcemap-upload-endpoint-defaults.md`), so this follows that convention.

Scope: how PostHog, FullStory, LogRocket, Microsoft Clarity, Hotjar/Contentsquare, Sentry, Datadog RUM, and Amplitude implement (1) frustration-signal detection, (2) grouping of signals into issues, (3) URL/path normalization, and (4) session activity classification. Each claim carries its own citation. Primary sources (vendor source code, vendor docs) are preferred, and anything not confirmed in a primary source is marked **UNVERIFIED**.

### Per-vendor details

**Sentry.** The SDK's `ClickDetector` only watches `A`, `BUTTON`, and `INPUT` (with `input` further restricted to `type=submit|button`). Links with `download` or a non-`_self` `target` are ignored. A click is a *slow click* if there was no scroll within `SLOW_CLICK_SCROLL_TIMEOUT = 300 ms` and no DOM mutation within `SLOW_CLICK_THRESHOLD = 3000 ms`; the overall timeout defaults to `slowClickTimeout = 7000 ms`. Clicks on the same node within 1 s are deduplicated to one reference and counted via `clickCount`, and `window.open` counts as a mutation. Mutations are derived from rrweb incremental sources (Mutation, StyleSheetRule, StyleDeclaration, AdoptedStyleSheet, CanvasMutation, Selection, MediaInteraction).
Sources: [handleClick.ts](https://github.com/getsentry/sentry-javascript/blob/main/packages/replay-internal/src/coreHandlers/handleClick.ts), [constants.ts](https://github.com/getsentry/sentry-javascript/blob/main/packages/replay-internal/src/constants.ts) (`SLOW_CLICK_THRESHOLD = 3_000`, `SLOW_CLICK_SCROLL_TIMEOUT = 300`), [integration.ts](https://github.com/getsentry/sentry-javascript/blob/main/packages/replay-internal/src/integration.ts) (`slowClickTimeout = 7_000`).
Server-side classification at ingest: a slow-click breadcrumb becomes a **dead click** when `endReason == "timeout"`, the tag is `a|button|input`, and `timeAfterClickMs >= 7000`. It becomes a **rage click** when additionally `clickCount >= 5`. Source: [event_parser.py](https://github.com/getsentry/sentry/blob/master/src/sentry/replays/usecases/ingest/event_parser.py).
The user-facing docs describe it as clicks that "don't lead to updates to the DOM or a page scroll within 7 seconds", with rage meaning "3 or more times within that 7-second timeframe". The docs' rage number (3) differs from the issue-creation threshold in server code (≥5). Source: [Rage click issues docs](https://docs.sentry.io/product/issues/issue-details/replay-issues/rage-clicks/), [Replay issues docs](https://docs.sentry.io/product/issues/issue-details/replay-issues/).

**Datadog RUM.** Docs: rage click = "A user clicks on an element more than three times in a one-second sliding window"; dead click = "clicks on a static element that produces no action on the page"; error click = "clicks on an element right before a JavaScript error occurs". Detection runs in the browser SDK (`trackUserInteractions: true`). Source: [Frustration signals docs](https://docs.datadoghq.com/real_user_monitoring/browser/frustration_signals/).
Source code specifics: a *click chain* accepts consecutive clicks only if they hit the same `event.target`, land ≤`MAX_DISTANCE_BETWEEN_CLICKS = 100` px apart (Euclidean), and arrive ≤1 s apart. `isRage` fires when any 3 clicks in the chain span ≤1 s (`MIN_CLICKS_PER_SECOND_TO_CONSIDER_RAGE = 3`) and no click in the chain saw selection or scroll activity. `isDead` requires no page activity and no input/scroll. It resolves `label[for]` to its control and excludes, via selector, textual `input`s, `textarea`, `select`, `[contenteditable]` (and descendants), `canvas`, and `a[href]` (and descendants). Page activity is validated within `PAGE_ACTIVITY_VALIDATION_DELAY = 100 ms`, and a click action is bounded by `CLICK_ACTION_MAX_DURATION = 10 s`.
Sources: [computeFrustration.ts](https://github.com/DataDog/browser-sdk/blob/main/packages/browser-rum-core/src/domain/action/computeFrustration.ts), [clickChain.ts](https://github.com/DataDog/browser-sdk/blob/main/packages/browser-rum-core/src/domain/action/clickChain.ts), [waitPageActivityEnd.ts](https://github.com/DataDog/browser-sdk/blob/main/packages/browser-rum-core/src/domain/waitPageActivityEnd.ts), [interactionSelectorCache.ts](https://github.com/DataDog/browser-sdk/blob/main/packages/browser-rum-core/src/domain/action/interactionSelectorCache.ts), [trackClickActions.ts](https://github.com/DataDog/browser-sdk/blob/main/packages/browser-rum-core/src/domain/action/trackClickActions.ts).

**PostHog.** Rage click (`$rageclick` event): defaults are `DEFAULT_CLICK_COUNT = 3`, `DEFAULT_THRESHOLD_PX = 30` (Manhattan distance, |dx|+|dy|, between consecutive clicks), and `DEFAULT_TIMEOUT_MS = 1000` between consecutive clicks. All three are configurable. Source: [rageclick.ts](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/extensions/rageclick.ts).
Dead click (`$dead_click`, a lazy-loaded extension): a click is *not* dead if within thresholds it saw scroll (`scroll_threshold_ms = 100`), selection change (`selection_change_threshold_ms = 100`), visibility change, or DOM mutation (`mutation_threshold_ms = 2500`). It *is* dead once a threshold is exceeded or the absolute timeout (`mutation_threshold_ms * 1.1` = 2750 ms) passes with no response. Checks run on a 1 s timer. Duplicate clicks on the same node within 1 s are ignored, modifier-key clicks and anchors are skipped, and `canvas,video,audio,embed,object` surfaces are exempt because mutations there are unobservable. Mobile "dead swipes" use a 30 px minimum movement and a budget of 10 per page load. Source: [dead-clicks-autocapture.ts (lazy entrypoint)](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/entrypoints/dead-clicks-autocapture.ts), wrapper: [extensions/dead-clicks-autocapture.ts](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/extensions/dead-clicks-autocapture.ts).

**Amplitude.** From source: `DEFAULT_RAGE_CLICK_THRESHOLD = 4` clicks within `DEFAULT_RAGE_CLICK_WINDOW_MS = 1_000` where the clicks' bounding box stays within `DEFAULT_RAGE_CLICK_OUT_OF_BOUNDS_THRESHOLD = 50` px; `DEFAULT_DEAD_CLICK_WINDOW_MS = 3_000` waiting for `mutation` or `navigate`; `ERROR_CLICK_TIMEOUT = 2_000` ("2 seconds to wait for an error to happen"). Rage clicks apply to any element (`DEFAULT_RAGE_CLICK_ALLOWLIST = ['*']`). Dead and error clicks only apply to an allowlist of interactive elements (`button`, `a`, roles `button|link|menuitem|option|tab|treeitem` etc., `[contenteditable]`, `input[type=button|submit|reset|image|file]`). Sources: [frustration-interactions.ts](https://github.com/amplitude/Amplitude-TypeScript/blob/main/packages/analytics-core/src/types/frustration-interactions.ts), [track-dead-click.ts](https://github.com/amplitude/Amplitude-TypeScript/blob/main/packages/plugin-autocapture-browser/src/autocapture/track-dead-click.ts), [track-rage-click.ts](https://github.com/amplitude/Amplitude-TypeScript/blob/main/packages/plugin-autocapture-browser/src/autocapture/track-rage-click.ts), [track-error-click.ts](https://github.com/amplitude/Amplitude-TypeScript/blob/main/packages/plugin-autocapture-browser/src/autocapture/track-error-click.ts). Docs describe frustration signals in the [Session Replay docs](https://amplitude.com/docs/session-replay/overview).

**FullStory.** Definitions only, no published numbers: rage = "clicking or tapping multiple times, rapidly, in the same area"; dead click = "clicks or taps that have no effect on the page … nothing on the page changes within a few seconds"; error click = "clicks or taps right before a client-side JavaScript error or console error occurs" (requires Console Data Capture); Thrashed Cursor = "desktop web sessions where users moved their mouse erratically or in circles". Source: [Frustration Signals help article](https://help.fullstory.com/hc/en-us/articles/360020624154-Rage-Clicks-Error-Clicks-Dead-Clicks-and-Thrashed-Cursor-Frustration-Signals).

**LogRocket.** Rage clicks "occur when a user clicks repeatedly in frustration on an element"; dead clicks "occur when a user clicks on an interactive element (button, link, etc), but the click had no visible effect (ie. a DOM change)". No thresholds published. Issue severity is computed with "machine learning and LLM" over a time range. Sources: [Issues docs](https://docs.logrocket.com/docs/issues), [Severe Issues docs](https://docs.logrocket.com/docs/severe-issues).

**Microsoft Clarity.** Rage click: "the user clicks multiple times in a clustered area in rapid succession". Dead click: "a user clicks on an element but gets no feedback in a reasonable amount of time … the visual status doesn't change, and there's no navigation away from the page". Excessive scrolling: "higher amounts of vertical scrolling than the expected average". Quick backs: "a user moves from a new to previous page in shorter time than defined threshold (the dwell time for that page)". Click errors: "JavaScript errors that occur after a user click". No numeric thresholds are published. Source: [Semantic metrics](https://learn.microsoft.com/en-us/clarity/insights/semantic-metrics).

**Hotjar / Contentsquare.** Contentsquare's own writing defines rage clicks only qualitatively ("repeatedly click … in a certain area or on a specific element … over a short period of time"): [Contentsquare rage clicks article](https://contentsquare.com/blog/rage-clicks/). The commonly cited Hotjar number, the same element clicked 5 times within 500 ms of one another, appears in third-party writeups of Hotjar's heatmap/filter behavior (e.g. [keycommerce](https://keycommerce.com/how-to-identify-rage-clicks-with-hotjar/), [Polaris Growth](https://www.polarisgrowth.com/en/blog/a-simple-way-to-detect-rageclicks-with-hotjar)). The Hotjar help-center pages returned 403 to automated fetching, so treat the 5-in-500ms figure as **UNVERIFIED**. Contentsquare's Frustration score is "computed using a machine learning algorithm trained on sessions with real user feedback" and operates at pageview, page-group, and session levels. Inputs surfaced in the replay event stream are "Rage clicks, Multiple Button Interaction, Multiple Field Interaction, and JS Errors": [Frustration score help article](https://support.contentsquare.com/hc/en-us/articles/37271767248273-Frustration-score) (support site blocks bot fetches; content confirmed via search excerpts of the article, so treat exact wording as approximate).

## 2. Grouping signals into issues

**Sentry.** The only vendor that promotes clicks into first-class issues, and it fingerprints on the selector alone. `report_rage_click_issue_with_replay_event` creates an issue occurrence with `fingerprint=[selector]`: the CSS selector path of the clicked element and nothing else. The page URL is not part of the grouping key. It becomes `culprit=url[:MAX_CULPRIT_LENGTH]` (display) and a `url` tag (searchable). The rrweb node and selector go into evidence. If a React component name is available it is added as the *important* evidence line, with the selector demoted to secondary, but the fingerprint stays `[selector]`. Environment is carried as a separate event field. Source: [issue_creation.py](https://github.com/getsentry/sentry/blob/master/src/sentry/replays/usecases/ingest/issue_creation.py).
Consequences: rage-click issues survive deploys, changing hostnames, and even page moves automatically. The cost is that two different pages sharing a selector like `button.btn-primary` collapse into one issue, and a selector change (CSS-module hash churn) forks the issue. Sentry does not document any selector normalization for these fingerprints (checked the docs and `event_parser.py`, which uses the SDK-provided breadcrumb `message` as the selector verbatim). Hydration-error issues from replays similarly use a single static fingerprint (`HYDRATION_ERROR_FINGERPRINT`), meaning one issue per project.

**Datadog** attaches `frustration.type` to *actions*, not separate issue objects. Aggregation happens in the RUM Explorer via facets, for example `action.frustration.type:rage_click` and `@session.frustration.count`, groupable by action name, `view.url_path`, or `view.url_path_group` (see §3). Actions carry a computed CSS selector for the target, and Datadog lets you pin identity with `data-dd-action-name`. No persistent "issue" entity is created from frustration signals. Sources: [Frustration signals docs](https://docs.datadoghq.com/real_user_monitoring/browser/frustration_signals/), [browser SDK action code](https://github.com/DataDog/browser-sdk/tree/main/packages/browser-rum-core/src/domain/action).

**PostHog** keeps `$rageclick` / `$dead_click` as plain events, with autocaptured element chain and URL properties. You aggregate them in insights yourself; there is no promotion to issues. Sources: [rageclick.ts](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/extensions/rageclick.ts), [dead-clicks entrypoint](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/entrypoints/dead-clicks-autocapture.ts) (events carry `autocapturePropertiesForElement` element-chain props).

**LogRocket** has an Issues product: "You can currently only group issues of the same type", with custom grouping rules available "for Errors, Network Errors, and Frustrating Requests". The automatic grouping key for rage/dead click issues (element vs page) is not documented. Source: [Issues docs](https://docs.logrocket.com/docs/issues). **UNVERIFIED** beyond that.

**FullStory** doesn't create issues. Frustration signals are session search criteria, filterable "via CSS selector or URL path filters", plus a built-in "Rage clicked recently" segment and Ragehooks (webhooks on rage click). Source: [Frustration Signals article](https://help.fullstory.com/hc/en-us/articles/360020624154), [Ragehooks](https://help.fullstory.com/hc/en-us/articles/360052984354-Ragehooks).

**Clarity** tags sessions and pageviews with the signal and exposes them as dashboard segments and filters; no issue objects. Source: [Semantic metrics](https://learn.microsoft.com/en-us/clarity/insights/semantic-metrics).

## 3. URL/path normalization

**Sentry (transaction clustering).** The most instructive design here. Two stages, fully server-side:
1. *Static scrubbing in Relay:* "Relay tests all incoming URL transactions against a static regex, and replaces matched groups with `*`", stripping "common identifiers such as UUIDs, integer IDs and hashes" (e.g. `/hash/4c79f60c…/diff/` → `/hash/*/diff/`).
2. *Learned clustering:* incoming URL transaction names are added to a per-project Redis set (sample capacity 2000). Hourly, a task splits names on `/` and builds a trie (a prefix tree). Where a node's children exceed the merge threshold, "set at 200" (raised from 100 to avoid merging genuinely static pages), it folds them into `*`, deriving glob rules like `/user/*/**` that are stored in project options and shipped to Relay for future events.
Hostname is not part of the transaction name for path-based transactions, and a cardinality limiter backstops anything that escapes scrubbing. Source: [Clustering URL Transactions (develop.sentry.dev)](https://develop.sentry.dev/backend/application-domains/transaction-clustering/).

**Datadog** generates `url_path_group` automatically: "The automatic URL group generated for similar URLs (for example, `/dashboard/?` for `/dashboard/123` and `/dashboard/456`)". ID segments are replaced with `?` server-side, and `view.url_path` (the raw path, no host) is kept alongside. Host lives in separate attributes, so the group key is host-free. Source: [RUM Browser Data Collected](https://docs.datadoghq.com/real_user_monitoring/browser/data_collected/).

**PostHog** uses manual, project-level regex **path cleaning rules**. Each rule is a regex plus an alias: "when a URL matches the regex, the matched portion is replaced with the alias. The rest of the URL remains unchanged" (e.g. regex `\/user\/\d+` with alias `/user/:id` turns `/user/123/profile` into `/user/:id/profile`). Rules apply to web analytics path tiles, to trends/funnels breakdowns on URL/pathname, and to Paths insights by default. The docs examples operate on paths, but rules run against the URL string, so a rule can also rewrite host parts. Source: [Path cleaning docs](https://posthog.com/docs/product-analytics/path-cleaning).

**FullStory** has user-defined Pages: "URL rules are how Fullstory understands how to group your pages under a definition". The syntax is token-based: `*` matches one token, `**` matches any suffix, `[a|b]` matches token alternatives, and when several rules match, "the most specific one will take precedent". Separately, search and grouping can target distinct URL *properties*: full URL, URL Host, URL Path ("starts right after the first slash after the host name" and "exclude[s] any fragments or queries"), URL Query, URL Fragment, URL Hash Query. Hostname and path are independent group-by dimensions. Sources: [Pages in Fullstory](https://help.fullstory.com/hc/en-us/articles/360052331173-Pages-in-Fullstory), [URL wildcards](https://help.fullstory.com/hc/en-us/articles/1500008550642-Can-I-search-for-URLs-using-wildcards), [Grouping by URL properties](https://help.fullstory.com/hc/en-us/articles/4411037492887-What-are-the-options-for-grouping-by-different-URL-properties).

**Clarity** offers regex path filters ("group together collections of similar pages so that you can see aggregated results for all of them") rather than automatic templating. Query parameters duplicate pages, and the community-recommended consolidation is the page-title custom tag. A distinct marketing term "smart URL grouping" was not found in Clarity's docs (**UNVERIFIED** that such a feature exists under that name). Sources: [Regular expressions for path filters](https://learn.microsoft.com/en-us/clarity/filters/regular-expressions), [Path filters](https://learn.microsoft.com/en-us/clarity/filters/path-filters-operators); the query-param and page-title point comes from a third-party guide ([dumbdata](https://dumbdata.co/post/10-innovative-ways-to-use-custom-tags-in-microsoft-clarity/)) and is **UNVERIFIED** in Microsoft docs.

**Amplitude**: no automatic URL templating found in the docs for session replay or autocapture page views. Replays are filtered by event and user properties, with page URL as a plain property. **UNVERIFIED** whether Amplitude offers any built-in page-path parameterization. Source checked: [Session Replay docs](https://amplitude.com/docs/session-replay).

**LogRocket**: no documented URL normalization for issue grouping found. **UNVERIFIED.**

Query-param handling: Sentry's transaction names and Datadog's `url_path`/`url_path_group` are path-based, with no query. FullStory's URL Path explicitly excludes query and fragment. PostHog path cleaning operates on whatever URL/pathname property the insight uses. Clarity treats differing query params as distinct pages by default (see above).

## 4. Session activity classification

**PostHog.** Session boundary: "A new session is started by default when either there's no activity for 30 minutes" or the 24-hour maximum duration is hit. "Activity is defined as any event sent from the client including autocapture events and replay activity like mouse movement", and the idle timeout is configurable via `session_idle_timeout_seconds`. Source: [Sessions docs](https://posthog.com/docs/data/sessions).
Recording activity ("active duration") from source: an rrweb event is *active* if it is an incremental snapshot with source in {MouseMove, MouseInteraction, Scroll, ViewportResize, Input, TouchMove, MediaInteraction, Drag}. An active segment stays active until `ACTIVITY_THRESHOLD_MS = 5000` passes without another active event. `activeMilliseconds` is the summed duration of active segments (a zero-length active segment counts as 1 ms), computed at ingestion by a cut-down copy of the player segmenter. Sources: [segmenter.ts](https://github.com/PostHog/posthog/blob/master/common/replay-shared/src/segmenter.ts), [ingestion segmentation.ts](https://github.com/PostHog/posthog/blob/master/nodejs/src/ingestion/pipelines/sessionreplay/segmentation.ts). The replay UI filters by "active duration" and by clicks, keypresses, mouse-activity counts, and console logs. Playback has "Skip inactivity, which skips parts of the recording where the user was inactive", and kiosk mode has "Minimum active duration – skip short recordings below a threshold in seconds". Source: [How to watch recordings](https://posthog.com/docs/session-replay/how-to-watch-recordings).

**Clarity.** Session: "A session ends if the user is inactive for 30 minutes." Inactive time is time the user left the site (e.g. on another domain). Source: [Glossary](https://learn.microsoft.com/en-us/clarity/setup-and-installation/glossary-of-terms). Traffic-quality classification (*User intent metrics*): **Low intent** = "less than 5 seconds on the site or staying longer without interacting (no clicks or scrolls)", described as bot-like; **Medium intent** = ">5 seconds … and interact to some extent"; **High intent** = ">5 seconds … actively interacting through clicks and key smart events". Source: [User intent metrics](https://learn.microsoft.com/en-us/clarity/insights/user-intent-metrics). ("Dead session" as a named Clarity concept is **UNVERIFIED**. The documented nearest equivalents are low-intent sessions and the "Inactive pages" insight, [Semantic metrics](https://learn.microsoft.com/en-us/clarity/insights/semantic-metrics).)

**Datadog.** "The session ends after 4 hours of activity or 15 minutes of inactivity." Frustration is aggregated per session as `@session.frustration.count`. Source: [RUM Browser Data Collected](https://docs.datadoghq.com/real_user_monitoring/browser/data_collected/), [Frustration signals](https://docs.datadoghq.com/real_user_monitoring/browser/frustration_signals/).

**Sentry.** The replay list has an **Activity** column: "The activity level as determined by the number of errors encountered, their duration, and the number of UI events", alongside Duration, Errors, Dead Clicks, and Rage Clicks columns. Source: [Replay page and filters](https://docs.sentry.io/product/explore/session-replay/web/replay-page-and-filters/).

**Amplitude.** Web sessions time out after 30 minutes of no events by default (configurable); mobile uses a 5-minute background gap. Source: [Track sessions docs](https://amplitude.com/docs/data/sources/instrument-track-sessions).

**FullStory / LogRocket / Hotjar.** No published activity-scoring formulas found. FullStory exposes "Frustrated Sessions" ([help article](https://help.fullstory.com/hc/en-us/articles/360020828013-Frustrated-Sessions)) and Contentsquare aggregates its Frustration score at session level (§1). **UNVERIFIED** beyond that.

The 30-minute inactivity timeout is the de facto convention (PostHog, Clarity, Amplitude web, also GA). Datadog is the outlier at 15 minutes with a 4-hour cap, and PostHog caps at 24 hours.

## 5. Implications for Opslane

Context, describing our current design rather than any vendor: friction buckets are keyed by `hash(signal_type | selector | normalized page URL)` and promoted at 5 distinct users in 7 days. Rage = ≥3 clicks within 1 s on the same selector. Dead = no mutation/request within 1 s (5 s for `option` elements). We just hit bucket fragmentation because the origin was in the URL key while Atlassian Forge serves apps from rotating per-deploy CDN hostnames.

1. Drop the origin from the bucket key. The precedent is unanimous: Sentry fingerprints rage-click issues on `[selector]` alone with the URL as display and tag only, Datadog's `url_path_group` and `view.url_path` are host-free, FullStory treats URL Host and URL Path as separate dimensions, and Sentry transaction names are host-free paths. No vendor keys stable groupings on hostname. Keeping the origin as a searchable attribute (Sentry's `url` tag pattern) preserves debuggability without fragmenting buckets. If we ever need host distinction for multi-tenant apps on one project, FullStory's model is the template: host as an optional extra group-by, not part of the identity.

2. Template IDs out of paths rather than matching exact paths. The cheapest robust option is Sentry Relay's stage 1: a static regex replacing integer, UUID, and long-hex segments with a placeholder (`*` / `:id`), which needs no configuration and kills most cardinality. Datadog's automatic `?`-substitution is the same idea. A learned stage (Sentry's trie with a threshold of 200 distinct children per node, recomputed hourly from a 2000-name sample) is the upgrade path if static scrubbing leaves high-cardinality slugs. User-configurable regex-plus-alias rules (PostHog) or token wildcards with most-specific-wins (FullStory) are worth copying later as an escape hatch, not as the default.

3. Our rage threshold is mainstream; our dead-click window is aggressive. Rage at ≥3 clicks in 1 s matches Datadog (3 in a 1 s sliding window) and PostHog (3 clicks ≤1 s apart) exactly. Amplitude wants 4 in 1 s, and Sentry's server wants ≥5 clicks plus a 7 s dead element. A proximity constraint like everyone else's (PostHog 30 px Manhattan, Amplitude 50 px box, Datadog 100 px plus same target) would be a minor addition; we already pin the selector, which is Datadog's same-target constraint. The dead-click side is different: our "no mutation/request within 1 s" is much shorter than every vendor. PostHog waits 2.5 s for mutations (100 ms for scroll/selection), Amplitude 3 s, Sentry 7 s (3 s mutation threshold, 300 ms scroll). Short windows misfire on slow backends, which are exactly the sessions where users are frustrated. Consider raising the mutation/request wait to somewhere between 2.5 and 3 s. Our 5 s `option` special case points the same direction as Datadog's exclusion of `select` and text inputs; Datadog and Amplitude solve that class of false positive by exempting element types rather than lengthening the window, so an exclusion list for text inputs, selects, contenteditable, and canvas would cut false positives further.

4. Promotion gating (5 users / 7 days) has no direct competitor analogue, and that's fine. Sentry promotes on the first qualifying rage click, one issue per selector, which produces noisy issues. LogRocket gates with ML severity. Datadog, PostHog, FullStory, and Clarity don't promote at all and lean on explorer/filter UX. Our distinct-user threshold is a reasonable middle ground; the closest published pattern is Contentsquare's impact-ranked Frustration score. One caution from Sentry's design: because their fingerprint is selector-only, a popular shared selector concentrates evidence. Since we key on selector plus path, our 5-user bar is harder to reach for the same real problem. After de-fragmenting hostnames, watch whether path templating (point 2) is also needed to stop `/projects/123` vs `/projects/456` splitting a bucket that would otherwise promote.

5. Session activity classification: the defensible defaults are a 30-minute inactivity boundary, and "active time" as rrweb-style interaction events (mouse/touch/scroll/input/media/drag) with a 5 s decay window (PostHog's `ACTIVITY_THRESHOLD_MS = 5000`), summed over segments. Clarity's low/medium/high intent shows a minimal viable classifier: under 5 s or zero interactions is low; interactions plus over 5 s is medium or high.
